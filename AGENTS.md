# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Corporate marketing site for İscotera (a software company), served at https://iscotera.com. Fully static Astro 7 + Tailwind CSS 4 build. The primary goals are SEO/brand visibility, so preserving the SEO plumbing (canonical, hreflang, sitemap, JSON-LD) on every page matters more than usual.

Repository: https://github.com/isco2225/iscotera. Site content is written in Turkish and English; **commit messages must be in English**, and code comments inside `src/` are written in Turkish to match the existing files.

`CLAUDE.md` is a symlink to this file (`AGENTS.md`), so both agent tools read the same guidance — edit `AGENTS.md`, never replace the symlink with a copy.

## Commands

Requires Node >= 22.12.0 (`engines` in package.json).

- `npm run dev` — dev server at localhost:4321. When starting it from an agent, use background mode: `astro dev --background` (manage with `astro dev stop` / `status` / `logs`). If dev throws `Cannot read properties of undefined` from a collection field that the build handles fine (seen 2026-09-01 as `reading 'appStore'` on every product page), the dev content cache `.astro/data-store.json` predates a schema change — the build keeps its own copy under `node_modules/.astro/`, so the two disagree. `astro dev --force` did not refresh it; stop the server, delete that one file and start again.
- `npm run build` — production build to `dist/`. Use this to verify changes; there are no tests or linter. Don't run `astro check`: `@astrojs/check` is not installed and the command blocks on an interactive install prompt. Type errors in `.astro` files surface in the editor (the Astro VS Code extension is the only recommended one) and, for anything that affects output, in the build.
- `npm run preview` — serve the production build locally.

Draft content (`draft: true` in frontmatter) renders in dev but is excluded from production builds — so dev and build page counts intentionally differ. The mechanism is not an Astro setting but a filter repeated in every `getCollection` call: `({ data }) => import.meta.env.DEV || !data.draft`. Any new listing, route or lookup over `blog` / `projects` must copy that predicate, or drafts leak into production.

## Architecture

### Bilingual routing (TR default, EN secondary)

- Turkish pages live at the root of `src/pages/` with Turkish slugs (`/hakkimizda/`, `/hizmetler/...`); English pages live under `src/pages/en/` with English slugs (`/en/about/`, `/en/services/...`). Astro's i18n config (`astro.config.mjs`) uses `defaultLocale: 'tr'` with no prefix for Turkish.
- Every page renders through `src/layouts/BaseLayout.astro`, which owns all SEO output: title suffixing, meta description, canonical URL, hreflang link tags, Open Graph tags, and Organization JSON-LD. Pages pass `lang` and an `alternate` prop (the same page's path in the other language); `alternate` drives both the hreflang tags and the header's language switcher. **When adding a page, add both language versions and wire `alternate` in both directions.** Blog detail pages are the deliberate exception (posts aren't 1:1 translated), so they omit `alternate`; the language switcher in `Header.astro` then falls back to the other language's home page, so it never dead-ends. Project detail pages pair themselves: if the same slug exists under both `tr/` and `en/`, the route passes `alternate` automatically; a project that exists in only one language simply gets none. `src/pages/404.astro` is the other single-language file: one Turkish-`lang` page with bilingual copy and links to both home pages, no `alternate`, no `back`.
- Static route pairs (TR path ↔ EN path) and all UI strings live in `src/i18n/ui.ts`. New nav items or translated labels go there, not inline in components. Components read them through `useTranslations(lang)` → `t('key')`; the key type is `keyof (typeof ui)[Lang]`, i.e. only keys present in **both** tables type-check, so every new string is added to `tr` and `en` together (the runtime `?? ui.tr[key]` fallback never actually fires). Page-specific structured data (`FAQPage`, `SoftwareApplication`, `VideoObject`) is injected through `BaseLayout`'s `head` slot (`<Fragment slot="head">`), never by writing a second `<head>`. The projects collection is presented as "Ürünler" / "Products" and its routes match: `/urunler/` and `/en/products/` (they were `/projeler/` and `/en/projects/` until 2026-08-29; the collection directory under `src/content/` is still named `projects/`, which is internal and stays English).
- Inner pages (everything but the two home pages) also pass `BaseLayout`'s `back` prop — `{ href, label }` pointing at the parent listing — which renders the back link above the content. Match this when adding a page; the label comes from `ui.ts`.

### Theming — semantic tokens, never literal colors

- **Never write a literal color utility in a page or component** (`bg-white`, `text-neutral-900`, `border-neutral-200`). Use the semantic tokens defined in `src/styles/global.css`: surfaces are `surface` / `surface-muted` / `surface-raised`, borders are `line` / `line-strong`, text runs `ink-strong` → `ink` → `ink-soft` → `ink-muted` → `ink-subtle` → `ink-faint`, and the accents are `brand`, `action` (filled-button background), `action-dark` (its hover) and `action-ink` (link/heading text). Their light values are exactly the Tailwind `neutral-*` tones the site used before (all declared in a single `@theme` block, so `bg-surface` / `text-ink-muted` etc. are ordinary Tailwind utilities), and `:root[data-theme='dark']` redefines them — so **a page that uses tokens gets dark mode for free and never needs a `dark:` variant.** The one literal that is allowed is `text-white` as the label on a filled `bg-action` button (and `bg-black/40` for the mobile-menu scrim): those sit on a colour that does not change between modes, so a token would only hide that.
- `action` and `action-ink` are the same blue in light mode but deliberately different in dark: no single blue is both readable as text on a dark ground and readable under white button text. Don't collapse them back into one.
- The mode lives in `data-theme` on `<html>`. `BaseLayout` writes it from `localStorage` (falling back to `prefers-color-scheme`) in an `is:inline` script that **must stay the first script in `<head>`** — bundling or deferring it brings back a white flash on every navigation in dark mode. The two-state control is `ThemeSwitch.astro`, rendered twice — once in the desktop nav, once in the header bar beside the hamburger under `md:hidden`, so mobile users reach it without opening the menu (the drawer deliberately has no third copy). Its knob position and icon emphasis come from `dark:` classes, not JavaScript, so it is already in the right position on first paint; the script only syncs `aria-checked` and persists the choice. Both instances carry `[data-theme-toggle]`, which is how the script finds them.
- The theme preference is the site's **only** browser storage, and there are no cookies anywhere in the codebase. It stores one key (`theme` = `"dark"` / `"light"`), first-party, never transmitted, no identifier — a UI preference set by the user's own click, which is the category consent rules exempt. So no consent banner is needed for it, and the `try/catch` around both calls is there because private-mode Safari and storage-blocked browsers throw. **Re-open this question when analytics lands** (it's on the README pre-launch list): the exemption reasoning here covers the theme toggle only and does not carry over.
- **Component-scoped `<style>` blocks do not survive the build.** Under this Astro + `@tailwindcss/vite` setup they are silently dropped from the output (verified 2026-08-29 with both a plain rule and a pseudo-element rule; the `data-astro-cid-*` attribute still lands in the HTML, but no matching CSS is ever emitted). No component in the repo relies on one. The rules Tailwind utilities genuinely can't express — `summary::-webkit-details-marker` for the FAQ accordion in Safari (`Faq.astro`, the one `<details>` accordion shared by `ServicePage` and `ProductPage`), and the `.process-fill` scroll-timeline keyframes for the home process section — live in `global.css` instead.
- **Never combine the `animation` shorthand with `animation-timeline` in one rule.** The CSS minifier folds them into a single shorthand, Chrome rejects that syntax and drops the whole animation (this happened, 2026-08-29). `.process-fill` is written as longhands: the base block starts `animation-play-state: paused` at the `scaleY(0)` frame, and only the `@supports (animation-timeline: view())` block, itself inside `prefers-reduced-motion: no-preference`, attaches the timeline and flips it to `running`. Keep that shape for any future scroll-linked rule.
- A `dark:` variant exists (`@custom-variant` in `global.css`) for the few things tokens can't reach: the icon swap in the theme button and `dark:prose-invert` on the three `prose` containers (both blog detail pages and the product story), since the typography plugin hardcodes its own colors.
- The İ logo appears in three places (`Header`, and the author line on both blog detail pages) and reads its tile fill from `--logo-tile` / `--logo-stroke`: in dark mode the tile lightens slightly and gains a hairline border, otherwise a black tile on a near-black page disappears. `public/favicon.svg` carries the same treatment via an embedded `prefers-color-scheme` query, and `brand/logo-dark.svg` is the dark-context source asset.

### Content model — four sources, four mechanisms

1. **Services** (`src/data/services.ts`): a single typed array holding an `id`, an optional `caseStudy` (a projects-collection slug, no language prefix) and, per language, slug/title/summary plus the detail-page content (`intro` paragraphs, `scope` cards, `approach` items, `faq`). The dynamic routes `src/pages/hizmetler/[slug].astro` and `src/pages/en/services/[slug].astro` both generate from it — adding an entry creates both detail pages and both listing cards automatically.
   - **Both detail routes render one component**, `src/components/ServicePage.astro` (same reasoning as `ProductPage`): the section order hero → scope → approach → case study → FAQ → CTA is the sales argument. The FAQ entries are real authored content, so the page also emits a `FAQPage` JSON-LD block via the layout's `head` slot.
   - `caseStudy` drives the "work we built with this" box on the detail page, and it only renders when that project entry is actually published (draft-aware `getEntry` check), so a draft product never produces a broken link in production.
   - **The services design is the photo showcase the user picked on a design canvas** (2026-08-29, "Yön D"): the listing is full-width alternating strips — `ServiceStrip.astro`, one per service, `surface-muted` band + red number + summary + photo, photo side alternating — and the detail page follows the same language (red index number in the hero, top-ruled scope columns, a `surface-muted` approach band with red step numbers). The photos live in `src/assets/services/<id>.jpg` (Pexels, free commercial license — sources and the no-visible-brands rule are in that folder's README.md) and each service's `imageAlt` lives per-language in `services.ts`; a service id with no matching photo renders as a single text column.
   - **CSS-drawn mockups and self-playing decorative animation are rejected here** (2026-08-29, two rounds before the photo direction settled): the user had hand-drawn CSS mockups and their micro-animations removed root and all. Real photography (or user-supplied media) is the accepted visual style; don't reintroduce drawn mockups or autoplaying motion, and run visual direction changes past the user on a canvas first. Motion tied to the visitor's own action is a different matter — see the home process section below, which the user asked for.
   - **Adding a service photo is two steps, not one**: drop `src/assets/services/<id>.jpg` in place *and* add it to the `images` map in `ServiceStrip.astro` (the map is explicit imports so Astro can optimize them; nothing is keyed by filename at runtime). The no-visible-brands rule in that folder's README applies to every photo under `src/assets/`.
2. **Blog and projects** (`src/content/blog/{tr,en}/`, `src/content/projects/{tr,en}/`): Markdown content collections defined in `src/content.config.ts`. Language is encoded in the entry id prefix (`tr/...` / `en/...`); listing and detail pages filter on it and strip it to form the URL slug. That schema file is the authoring contract — the project frontmatter carries far more than title/description (`logo`, `cover`, `features`, `results` capped at 3, `stores`, `rating`, `testimonials`, `faq`, `app`, `social`, `links`, `order`), so read it before hand-writing an entry. The product page renders hero → proof strip → features → story → testimonials → FAQ → closing CTA, and any section whose field is empty is not rendered at all; there is deliberately no separate screenshot gallery (each screen sits beside the feature it illustrates) and no pricing section (`pricing.label` shows as a chip in the hero). The blog sample templates (`blog/tr/ornek-yazi.md`, `blog/en/sample-post.md`) are permanent drafts kept as authoring documentation — don't publish or delete them. The projects collection has no sample entry any more: the user had `ornek-proje.md` / `sample-project.md` removed on 2026-09-01, so the schema comments in `content.config.ts` and the two published entries are the reference for product frontmatter; don't recreate a sample product.
   - **Product teasers are full-width showcase strips**, not boxed cards: `src/components/ProductStrip.astro` (the "Yön 1" the user picked on the products design canvas, 2026-08-29) renders each product as a `surface-muted` band — logo + title, a status chip with a brand-red dot (same language as the logo's dot), a quiet `category · platforms` line, a large tagline, big result numbers and a shadowed cover capped with `object-cover` — used by both home pages and both product listings, alternating background and image side by `index` like `ServiceStrip`.
   - **A product's promo video replaces the hero cover without costing the first paint** (frontmatter `video: { src, uploadDate }`, file under `public/media/<slug>/` — Astro doesn't process video). The cover stays as the `poster` so LCP is unchanged; `preload="none"` plus a visibility script means the file streams only once the hero is seen (muted, looped, no controls), a reduced-motion visitor gets a paused video with controls instead, and the page emits a `VideoObject` schema because the video really plays on the page.
   - **Both product routes render one component.** `/urunler/[slug]` and `/en/products/[slug]` are thin: they only choose which entry is published where (and pair the two languages for `alternate`); the whole page body lives in `src/components/ProductPage.astro`. The rest of the site is written per language, but the product page deliberately is not — its section order is the sales argument, and two copies would silently drift. Change the page there, and change the strings in `ui.ts`.
   - **The İbadet Rehberim entry is deliberately thin.** It is not a sales page for the app (ibadetrehberim.com already is one); its job is to show a prospective client "we built this, this is how". So it intentionally has no `faq`, no `testimonials`, no `rating` (only the verifiable download count in `results`) and only two of the app's features — the ones that show engineering decisions. Don't fill those sections in to make the page "complete"; the pre-launch checklist in README.md says exactly what still has to land (the App Store link, then `draft: false` in both languages).
   - **Dernek Asistan is a client case study** (`type: case-study`, client Vefa Yolu Derneği, an internal staff tool): no `stores`, no `pricing`, and deliberately no `app` block, so the page emits no `SoftwareApplication` schema — reporting an offer and install URL for software nobody can obtain would be fiction. `results` is empty because there are no verified usage figures; the prose describes the benefits qualitatively instead. Its screenshots were chosen to contain no donor names or phone numbers; keep it that way when adding more.
   - **Unverified data renders but never enters the schema.** Two frontmatter escape hatches let a page be laid out before the real facts arrive: `placeholderData: ['rating', 'testimonials']` marks a field as made-up (it still shows on the page but is left out of the JSON-LD), and `stores.pending: ['appStore']` marks a store link we don't have yet (the badge prints as a dim, unclickable placeholder — never the official badge art, which is licensed for a link that actually goes to the store). Both exist because reporting an invented `aggregateRating` or review in structured data violates Google's rules and earns a manual action. `warnUnfinishedData` in `src/utils/product.ts` prints a build warning for every entry that still has either list populated, so `npm run build` is the check — **both lists must be empty before an entry flips to `draft: false`.**
3. **Contact details** (`src/data/contact.ts`): the single source for e-mail, phone (display + E.164), WhatsApp and Instagram. The contact pages, the footer, and the Organization JSON-LD in `BaseLayout` all read from it — change the constant, never the markup.
4. **Static pages** (home, about, contact): copy is written inline per language in the page files, so a wording change is made twice (`src/pages/x.astro` and `src/pages/en/x.astro`). Home and contact carry real copy; About is still three `PagePlaceholder` notes in both languages (the same component renders the empty states of the blog and product listings). Real copy replaces the notes and the component disappears from the page as content lands.
   - **The home process section** ("Çalışma sürecimiz") is a sticky intro column (label, heading, CTA, the team photo from `src/assets/home/team.jpg` — Pexels, source in that folder's README) beside a red-numbered vertical timeline whose guide line fills red as the visitor scrolls. The fill is `.process-fill` in `global.css`, driven by `animation-timeline: view()` — it moves only when the page moves, which is why it is allowed under the no-decorative-motion rule; browsers without scroll timelines and reduced-motion visitors get the plain grey line. The user asked for this explicitly (2026-08-29), and the layout was modelled on an agency site they liked. The `steps` array (title, thesis, text) lives in each home page's frontmatter; the copy makes promises (two-week release cadence, maintenance after launch) that must stay true, so don't sharpen them for effect.

### Deliberate decisions (don't "fix" these)

- **Brand palette is white/black/red, plus one blue for actions** (see the next bullet). Red is an accent color only — logo, step numbers, card hover borders — never a background or text color for content. It lightens to `#ff4d57` in dark mode because `#e50914` drops below the contrast threshold on a dark ground.
- **Orange was tried and rejected** (2026-08-28, at the user's request then their call to drop it). Two things killed it: white text on any real orange lands at 2.8:1, so an orange button would have needed dark text and become the only dark-text button on the site; and orange can't be a text color on white at all, making it a fill-only half-color. It also sits ~28° from the brand red, close enough to read as "the red slipped" rather than a second color. Don't reintroduce it as a third accent without a job of its own.
- **Filled buttons are blue, not red** (changed 2026-08-28 at the user's request): a filled red rectangle reads as "delete / cancel / warning", the wrong signal for a confirming action. Primary buttons use the `--color-action` / `--color-action-dark` tokens (`bg-action` / `hover:bg-action-dark`) defined in `src/styles/global.css`; secondary buttons stay outlined neutral. Black was tried first and rejected as not eye-catching enough. The rule that settled out of this: **blue means clickable, red means brand.** Anything that invites a click — filled buttons, "read more" links, the colour a card title turns on hover — uses `action`; red is reserved for identity and decoration: the logo, the step numbers on the home page, the `hover:border-brand/40` card outline.
- **Language coverage is asymmetric on purpose.** Turkish has published blog posts; English has none, so `/en/blog/` renders the `blog.empty` string. Of the two real products, Dernek Asistan is published in both languages and İbadet Rehberim is still `draft: true` in both (waiting on its App Store link), so production listings show one strip. The empty English blog is expected output, not a bug to chase.
- **Logo and favicon are the İ monogram** (black tile, white body with a diagonal cut, red dot centered above). Sources live in `brand/` (`logo.svg` plus PNG exports at 256/512/1024); the deployed favicon is `public/favicon.svg`, and `BaseLayout` also points the JSON-LD `logo` field at it. If the mark changes, regenerate all of them together.
- **Names inside `src/` are English, content is Turkish.** Asset folders and image files use English names (`_images/`, `screen-prayer-times.png`) even though the copy they carry is Turkish. The Turkish segments under `src/pages/` are the deliberate exception — those are the public URLs, not internal names. Project images live in `src/content/projects/_images/<proje-slug>/` and are referenced from frontmatter with paths relative to the markdown file, so Astro optimizes them (`image()` in the collection schema).
- **Each product image is generated with exactly one set of options**, from `productImageOptions(image)` in `src/utils/product.ts`: portrait phone screens get `PRODUCT_IMAGE_WIDTH` (640) at default quality; landscape desktop screenshots (Dernek Asistan) get `PRODUCT_WIDE_IMAGE_WIDTH` (1984) at `quality: 'max'`, because default WebP compression smears fine UI text (WebP is still ~40 KB at that setting). Asking for the same source with a second set of options makes Astro emit a second file that the browser also downloads, and `ProductPage` builds the JSON-LD `screenshot` URLs from the same call as the visible `<img>`, so every component must spread the helper rather than pass its own `width`/`quality`. Each width is 2× the widest place that shape is displayed, so 2× screens don't upscale it — which means **desktop screenshots must be captured at DPR 2** (Chrome DevTools device toolbar → DPR 2 → Capture screenshot; a 1× capture is built at its own width and stays soft on Retina; Astro never enlarges). `isLandscape()` also switches the layout: a phone screen sits beside the text in a capped column (and is cropped in the strip), a landscape shot drops below the text at full container width in the hero and the feature rows, and gets equal columns in the strip. Change the constants, not the individual `<Image>` calls.
- **Store badge art is optional at build time.** `StoreBadges.astro` checks `public/badges/` on disk and falls back to its own text button when the official SVG/PNG is missing, so the repo builds without shipping Apple's and Google's assets. The brand constraints it encodes (App Store first, equal 48px heights, no recolouring or cropping, untranslated wordmarks, one file per language) come from those vendors' guidelines — `public/badges/README.md` has the download links and the rules.
- The sitemap integration emits hreflang alternates itself (configured in `astro.config.mjs`); `public/robots.txt` points to `/sitemap-index.xml`.
- Remaining pre-launch TODOs (og:image, contact form backend, hosting + DNS, Search Console, analytics) are tracked in README.md, which is written in Turkish and doubles as the content-authoring guide. Keep its checklist in sync when one lands; the matching `TODO:` comments sit in `BaseLayout.astro`.
