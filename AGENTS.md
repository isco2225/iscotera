# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Corporate marketing site for İscotera (a software company), served at https://iscotera.com. Fully static Astro 7 + Tailwind CSS 4 build. The primary goals are SEO/brand visibility, so preserving the SEO plumbing (canonical, hreflang, sitemap, JSON-LD) on every page matters more than usual.

It is hosted on Vercel (project `iscotera`). The apex `iscotera.com` is the production domain, and `www.iscotera.com` and `iscotera.vercel.app` 308-redirect to it. **The Vercel primary domain and `site` in `astro.config.mjs` must name the same host**, because every canonical, the sitemap, `robots.txt` and the JSON-LD `@id`s are built from `site`. Until 2026-09-29 Vercel redirected the apex to `www` while all of those pointed at the apex, so every canonical led to a redirect. That was fixed in the Vercel dashboard, not in code. Check with `curl -sI https://www.iscotera.com/`, which should answer with a 308 to the apex. `vercel.json` sets `trailingSlash: true` (added 2026-10-07), so `/hakkimizda` 308-redirects to `/hakkimizda/` instead of serving a duplicate that Search Console lists as an "alternate page with proper canonical tag"; paths with a file extension are not affected. Every internal link already ends in `/`, so keep it that way.

Repository: https://github.com/isco2225/iscotera. Site content is written in Turkish and English; **commit messages must be in English**, and code comments inside `src/` are written in Turkish to match the existing files.

`CLAUDE.md` is a symlink to this file (`AGENTS.md`), so both agent tools read the same guidance — edit `AGENTS.md`, never replace the symlink with a copy.

## Commands

Requires Node >= 22.12.0 (`engines` in package.json).

- `npm run dev` — dev server at localhost:4321. When starting it from an agent, use background mode: `astro dev --background` (manage with `astro dev stop` / `status` / `logs`). If dev throws `Cannot read properties of undefined` from a collection field that the build handles fine (seen 2026-09-01 as `reading 'appStore'` on every product page), the dev content cache `.astro/data-store.json` predates a schema change — the build keeps its own copy under `node_modules/.astro/`, so the two disagree. `astro dev --force` did not refresh it; stop the server, delete that one file and start again.
- `npm run build` — production build to `dist/` (about a second). Use this to verify changes; there are no tests or linter. The build fails on frontmatter that breaks the `content.config.ts` schemas and on anything that throws while prerendering, but it does not type-check, and neither `typescript` nor `@astrojs/check` is installed. Don't run `astro check`: it blocks on an interactive install prompt. A pure type error (a wrong prop, a string missing from one `ui.ts` table) therefore shows up only in the editor (the Astro VS Code extension is the only recommended one).
- `npm run preview` — serve the production build locally. From an agent, use `astro preview --background`, which takes the same `stop` / `status` / `logs` subcommands. Both servers default to port 4321, so pass `--port` when dev is already running.

Draft content (`draft: true` in frontmatter) renders in dev but is excluded from production builds — so dev and build page counts intentionally differ. The mechanism is not an Astro setting but a filter repeated in every `getCollection` call: `({ data }) => import.meta.env.DEV || !data.draft`. Any new listing, route or lookup over `blog` / `projects` must copy that predicate, or drafts leak into production.

## Architecture

### Bilingual routing (TR default, EN secondary)

- Turkish pages live at the root of `src/pages/` with Turkish slugs (`/hakkimizda/`, `/hizmetler/...`); English pages live under `src/pages/en/` with English slugs (`/en/about/`, `/en/services/...`). Astro's i18n config (`astro.config.mjs`) uses `defaultLocale: 'tr'` with no prefix for Turkish.
- Every page renders through `src/layouts/BaseLayout.astro`, which owns all SEO output: title suffixing, meta description, canonical URL, hreflang link tags, Open Graph tags, and the site-wide JSON-LD `@graph` (see the structured-data bullet below). Pages pass `lang` and an `alternate` prop (the same page's path in the other language); `alternate` drives both the hreflang tags and the header's language switcher. **When adding a page, add both language versions and wire `alternate` in both directions.** Blog detail pages are the deliberate exception (posts aren't 1:1 translated), so they omit `alternate`; the language switcher in `Header.astro` then falls back to the other language's home page, so it never dead-ends. Project detail pages pair themselves: if the same slug exists under both `tr/` and `en/`, the route passes `alternate` automatically; a project that exists in only one language simply gets none. `src/pages/404.astro` is the other single-language file: one Turkish-`lang` page with bilingual copy and links to both home pages, no `alternate`, no `back`.
- Static route pairs (TR path ↔ EN path) and the labels that shared components render live in `src/i18n/ui.ts`; per-language page files write their own copy inline (see Static pages below). New nav items or translated labels go into `ui.ts`, not inline in components. Components read them through `useTranslations(lang)` → `t('key')`. The key type is `keyof (typeof ui)[Lang]`, so only keys present in **both** tables type-check. The source spells it `typeof defaultLang`, which resolves to `Lang` only because `defaultLang` is annotated `: Lang`, so keep that annotation. Every new string is therefore added to `tr` and `en` together, and the runtime `?? ui.tr[key]` fallback never fires as long as the editor's type errors are respected. The projects collection is presented as "Ürünler" / "Products" and its routes match: `/urunler/` and `/en/products/`. They were `/projeler/` and `/en/projects/` until 2026-08-29. The collection directory under `src/content/` is still named `projects/`, and so are the `routes.*.projects` / `nav.projects` keys in `ui.ts`: these are internal names and stay English.
- Inner pages (everything but the two home pages) also pass `BaseLayout`'s `back` prop — `{ href, label }` pointing at the parent listing — which renders the back link above the content. Match this when adding a page. `ServicePage` and `ProductPage` take the label from `ui.ts`; the per-language page files write it inline.
- **Structured data is one `@graph` per page plus optional page-specific blocks.** `BaseLayout` emits a single `application/ld+json` script holding `Organization` (every page, with `@id` `#organization`), `WebSite` (the two home pages only, `@id` `#website`) and `BreadcrumbList` — the breadcrumbs are derived from the `back` prop (home → `back.label` → page title, dropping the middle crumb when the parent *is* home), so a wrong `back` is also wrong SEO output, not just a wrong link. The `@id` helpers and `localeTag` live in `src/utils/schema.ts`; a page-level schema that needs the company references `{ '@id': organizationId(Astro.site) }` instead of restating name/logo/contact. Blog detail pages build their `BlogPosting` from `blogPostingSchema()` in that file (one helper so the two language routes can't drift; author and publisher are both the Organization, matching the visible "İscotera Ekibi" byline), and its `image` is the post's cover when one exists (the same `getImage()` output as the visible `<img>`, so the URL always exists) and absent otherwise — pointing at a missing URL is a Search Console error. Page-specific blocks (`FAQPage` on service and product pages, `SoftwareApplication` / `VideoObject` on product pages, `BlogPosting`, `AboutPage`) go through `BaseLayout`'s `head` slot (`<Fragment slot="head">`, never a second `<head>`) as separate scripts; don't merge them into the layout graph.

### Theming — semantic tokens, never literal colors

- **Never write a literal color utility in a page or component** (`bg-white`, `text-neutral-900`, `border-neutral-200`). Use the semantic tokens defined in `src/styles/global.css`: surfaces are `surface` / `surface-muted` / `surface-raised`, borders are `line` / `line-strong`, text runs `ink-strong` → `ink` → `ink-soft` → `ink-muted` → `ink-subtle` → `ink-faint`, and the accents are `brand`, `action` (filled-button background), `action-dark` (its hover) and `action-ink` (link/heading text). Their light values are exactly the Tailwind `neutral-*` tones the site used before (all declared in a single `@theme` block, so `bg-surface` / `text-ink-muted` etc. are ordinary Tailwind utilities), and `:root[data-theme='dark']` redefines them — so **a page that uses tokens gets dark mode for free and never needs a `dark:` variant.** Literals are allowed only on a colour that does not change between modes, where a token would only hide that. That means `text-white` as the label on a filled `bg-action` button, `bg-black/40` for the mobile-menu scrim, and the contents of a product panel (`ProductPanel.astro`), which sits on the product's own colour: its white text, its white pill button with `text-neutral-900`, and its `green-400` live dot.
- `action` and `action-ink` are the same blue in light mode but deliberately different in dark: no single blue is both readable as text on a dark ground and readable under white button text. Don't collapse them back into one.
- The mode lives in `data-theme` on `<html>`. `BaseLayout` writes it from `localStorage` (falling back to `prefers-color-scheme`) in an `is:inline` script that **must stay the first script in `<head>`** — bundling or deferring it brings back a white flash on every navigation in dark mode. The two-state control is `ThemeSwitch.astro`, rendered twice — once in the desktop nav, once in the header bar beside the hamburger under `md:hidden`, so mobile users reach it without opening the menu (the drawer deliberately has no third copy). Its knob position and icon emphasis come from `dark:` classes, not JavaScript, so it is already in the right position on first paint; the script only syncs `aria-checked` and persists the choice. Both instances carry `[data-theme-toggle]`, which is how the script finds them. The inline script defines `window.__setTheme(theme)`, which sets `data-theme`, updates the `<meta name="theme-color">` (the mobile browser-bar colour can't follow `prefers-color-scheme` because the user may pick the opposite of their system setting) and syncs `aria-checked`; `Header.astro`'s toggle calls that same global rather than duplicating the logic, so a new colour value is changed in one place.
- The theme preference is the site's **only** browser storage, and there are no cookies anywhere in the codebase. It stores one key (`theme` = `"dark"` / `"light"`), first-party, never transmitted, no identifier — a UI preference set by the user's own click, which is the category consent rules exempt. So no consent banner is needed for it, and the `try/catch` around both calls is there because private-mode Safari and storage-blocked browsers throw. **Re-open this question when analytics lands** (it's on the README pre-launch list): the exemption reasoning here covers the theme toggle only and does not carry over.
- **Component-scoped `<style>` blocks do work, but they don't land in the CSS bundle.** Astro inlines small stylesheets (`build.inlineStylesheets: 'auto'`) as a `<style>` in the `<head>` of every page that renders the component, so to check that a rule shipped, grep the built HTML, not `dist/_astro/*.css` (re-verified 2026-09-23 with the Safari marker rule in `Faq.astro`). The rules Tailwind utilities can't express still live in `global.css`: `summary::-webkit-details-marker` for the FAQ accordion in Safari (`Faq.astro`, the one `<details>` accordion shared by `ServicePage` and `ProductPage`), the `.process-fill` scroll-timeline keyframes for the home process section and the `.hero-*` layers.
- **Never combine the `animation` shorthand with `animation-timeline` in one rule.** The CSS minifier folds them into a single shorthand, Chrome rejects that syntax and drops the whole animation (this happened, 2026-08-29). `.process-fill` is written as longhands: the base block starts `animation-play-state: paused` at the `scaleY(0)` frame, and only the `@supports (animation-timeline: view())` block, itself inside `prefers-reduced-motion: no-preference`, attaches the timeline and flips it to `running`. Keep that shape for any future scroll-linked rule.
- A `dark:` variant exists (`@custom-variant` in `global.css`) for the few things tokens can't reach: the icon swap in the theme button and `dark:prose-invert` on the three `prose` containers (both blog detail pages and the product story), since the typography plugin hardcodes its own colors.
- The İ logo is one component, `src/components/Logo.astro` (size via `class`), used in `Header`, `Footer` and the author line on both blog detail pages; it reads its tile fill from `--logo-tile` / `--logo-stroke`: in dark mode the tile lightens slightly and gains a hairline border, otherwise a black tile on a near-black page disappears. `public/favicon.svg` carries the same treatment via an embedded `prefers-color-scheme` query, and `brand/logo-dark.svg` is the dark-context source asset.

### Content model — four sources, four mechanisms

The per-page and per-product reasoning (what the user picked, rejected and why) lives in `docs/content-decisions.md`, which is not loaded automatically. The bullets below give the rules; read that file before editing a product entry, the product panel, the footer, the About page or the home pages.

1. **Services** (`src/data/services.ts`): a single typed array holding an `id`, an optional `caseStudy` (a projects-collection slug, no language prefix) and, per language, slug/title/summary plus the detail-page content (`intro` paragraphs, `scope` cards, `approach` items, `faq`). The dynamic routes `src/pages/hizmetler/[slug].astro` and `src/pages/en/services/[slug].astro` both generate from it — adding an entry creates both detail pages and both listing cards automatically.
   - **Both detail routes render one component**, `src/components/ServicePage.astro` (same reasoning as `ProductPage`): the section order hero → scope → approach → case study → FAQ → CTA is the sales argument. The FAQ entries are real authored content, so the page also emits a `FAQPage` JSON-LD block via the layout's `head` slot.
   - `caseStudy` drives the "work we built with this" box on the detail page, and it only renders when that project entry is actually published (draft-aware `getEntry` check), so a draft product never produces a broken link in production.
   - **The services design is a photo showcase.** The listing is full-width alternating strips (`ServiceStrip.astro`, one per service: `surface-muted` band, red number, summary, photo on alternating sides), and the detail page uses the same language (red index number in the hero, top-ruled scope columns, a `surface-muted` approach band with red step numbers). Each service's `imageAlt` lives per language in `services.ts`; a service id with no matching photo renders as a single text column.
   - **Real photography is the accepted visual style.** CSS-drawn mockups and self-playing decorative animation were removed at the user's request; don't reintroduce them, and run visual direction changes past the user on a canvas first. Motion driven by the visitor's own scroll is allowed (the home process section). History in `docs/content-decisions.md`.
   - **Adding a service photo is two steps, not one**: drop `src/assets/services/<id>.jpg` in place *and* add it to the `images` map in `ServiceStrip.astro` (the map is explicit imports so Astro can optimize them; nothing is keyed by filename at runtime). The no-visible-brands rule in that folder's README applies to every photo under `src/assets/`.
2. **Blog and projects** (`src/content/blog/{tr,en}/`, `src/content/projects/{tr,en}/`): Markdown content collections defined in `src/content.config.ts`. Language is encoded in the entry id prefix (`tr/...` / `en/...`); listing and detail pages filter on it and strip it to form the URL slug. That schema file is the authoring contract — the project frontmatter carries far more than title/description (`logo`, `cover`, `features`, `results` capped at 3, `stores`, `rating`, `testimonials`, `faq`, `app`, `social`, `links`, `screenshotsIllustrative`, `order`), so read it before hand-writing an entry. The product page renders hero → proof strip → features → story → testimonials → FAQ → related services → closing CTA, and any section whose field is empty is not rendered at all; there is deliberately no separate screenshot gallery (each screen sits beside the feature it illustrates) and no pricing section (`pricing.label` shows as a chip in the hero). Blog entries take an optional `cover` + `coverAlt` (file under `src/content/blog/_images/<slug>/cover.jpg`, Pexels sources and the no-visible-brands rule in that folder's README): the listing and home teasers show it as a full-width 21:9 band above the text via `<Image>` with `blogThumbOptions` (1408 wide, cropped to 21:9 at build time at the detail cover's quality, because the listing shows ten covers per page; side-by-side thumbnails and a taller 16:9 band were both rejected), the detail page shows it wide via one `getImage()` call with `blogCoverOptions` (1536 wide, cropped to 16:9 at build time at quality 70, since it is the page's LCP element) whose URL also feeds the `BlogPosting.image` — the constants live in `src/utils/blog.ts`, so change them there rather than in the calls. The blog listings are paginated (since 2026-10-07, the user's call, as a trial): `src/pages/blog/[...page].astro` and `src/pages/en/blog/[...page].astro` use Astro's `paginate()` with `BLOG_PAGE_SIZE` (10) from `src/utils/blog.ts`, so page one stays `/blog/` and later pages are `/blog/2/`, `/blog/3/` (built with `blogPageUrl()`, which also feeds `rel="prev"`/`"next"` and the shared `Pagination.astro`). From page two on, the title and description carry the page number, `alternate` is omitted (the other language has no matching page) and `back` points at the blog's first page, so the breadcrumb reads Home → Blog → page. The `[...page]` route sits beside `[slug].astro` in the same folder; Astro tells them apart by what each `getStaticPaths` returns, so a post must never be given a purely numeric slug. The `_images` folders are excluded from both collection globs so their README is not parsed as an entry. There are no sample/template entries in either collection (removed at the user's request); the schema comments in `content.config.ts`, the README's authoring section and the published entries are the reference, so don't recreate a sample post or product.
   - **Product teasers are product-coloured panels** (`src/components/ProductPanel.astro`, on both home pages and both product listings). Each product is one rounded panel and the whole panel is a single link. It sits on the product's frontmatter `color` (neutral `#262626` when unset); the schema rejects a colour under 7:1 contrast with white (`contrastWithWhite` in `src/utils/color.ts`). Its button is a white pill, not the site blue, which clashes on a coloured ground. Both listings mark their first panel `eager`, because it can be the LCP element. **The compact phone layout below `md:` relies on a `display: contents` grid arrangement that is easy to break**: read the Product panels section of `docs/content-decisions.md` before changing the panel's markup.
   - **A product's promo video replaces the hero cover without costing the first paint** (frontmatter `video: { src, uploadDate }`, file under `public/media/<slug>/` — Astro doesn't process video). The cover stays as the `poster` so LCP is unchanged; `preload="none"` plus a visibility script means the file streams only once the hero is seen (muted, looped, no controls), a reduced-motion visitor gets a paused video with controls instead, and the page emits a `VideoObject` schema because the video really plays on the page.
   - **The product hero carries a künye (client + sector), never a year or a company-wide count.** `client` and `sector` render as a small two-column `<dl>` under the tagline; `year` stays in frontmatter but is deliberately not printed (the same year under every entry would advertise how young the company is, not the project), and there is no "N+ projects / N+ clients" band anywhere — the user ruled both out on 2026-09-21 after comparing with a larger competitor's site. The only figures shown are the per-product `results`. The related-services block ("services we used on this project", just before the closing CTA) is derived by reverse lookup of `caseStudy` in `services.ts` (no extra frontmatter), so service → case study → service is a closed loop for internal linking.
   - **Both product routes render one component.** `/urunler/[slug]` and `/en/products/[slug]` are thin: they only choose which entry is published where (and pair the two languages for `alternate`); the whole page body lives in `src/components/ProductPage.astro`. The rest of the site is written per language, but the product page deliberately is not — its section order is the sales argument, and two copies would silently drift. Change the page there, and change the strings in `ui.ts`.
   - **Each published product entry leaves sections out on purpose.** İbadet Rehberim has no `faq`, `testimonials` or `rating` and no App Store link yet (add `stores.appStore` when it ships). QR Menü is a deliberately short summary with no prices, no `app` block and no testimonials. Dernek Asistan names no client anywhere in the project, this repo included, and has no `app` block and no feature screenshots. Don't fill sections in to make a page look complete, and don't expand QR Menü. **Read the entry's section in `docs/content-decisions.md` before editing any product.**
   - **Case-study copy is written for the client's manager, not for an engineer.** It is short and benefit-first, with no implementation vocabulary and no screen-level detail (tabs, fields, form steps). Each feature `title` is a benefit headline, each `text` is at most two sentences, and claims stay qualitative while there are no verified figures. The stack and the schema belong in a blog post if anywhere. Examples of what was cut are in `docs/content-decisions.md`.
   - **Unverified data renders but never enters the schema.** Two frontmatter escape hatches let a page be laid out before the real facts arrive: `placeholderData: ['rating', 'testimonials']` marks a field as made-up (it still shows on the page but is left out of the JSON-LD), and `stores.pending: ['appStore']` marks a store link we don't have yet (the badge prints as a dim, unclickable placeholder — never the official badge art, which is licensed for a link that actually goes to the store). Both exist because reporting an invented `aggregateRating` or review in structured data violates Google's rules and earns a manual action. `warnUnfinishedData` in `src/utils/product.ts` prints a build warning for every entry that still has either list populated, so `npm run build` is the check — **both lists must be empty before an entry flips to `draft: false`.** Note the warning fires from `ProductPage`, i.e. only for entries that actually get a page: a `draft: true` entry is silent under `npm run build` and only warns in dev (when its page is rendered), so run the check right after flipping the flag, not before.
3. **Contact details** (`src/data/contact.ts`): the single source for e-mail, phone (display + E.164), WhatsApp and Instagram. The contact pages, the footer, and the Organization JSON-LD in `BaseLayout` all read from it — change the constant, never the markup. The channel icons (mail, phone, WhatsApp, Instagram) are one component, `ContactIcon.astro`, shared by `ContactCard` and the footer.
   - **The footer** is four columns (brand, pages, services, contact) plus a copyright row. The services column lists every entry in `services.ts`, so each service page gets a site-wide internal link. The copyright row carries the other-language link (`alternate` from `BaseLayout`, falling back to the other home page). It deliberately has no privacy/KVKK links, because those pages don't exist while the site has no cookies and no form; add them there when the contact form or analytics lands. Layout details are in `docs/content-decisions.md`.
4. **Static pages** (home, about, contact): copy is written inline per language in the page files, so a wording change is made twice (`src/pages/x.astro` and `src/pages/en/x.astro`). All three now carry real copy; `PagePlaceholder` survives only as the empty state of the blog and product listings.
   - **The About page argues from principles, never from figures.** It has no counts, no founding year, no mention of being young and no Misyon/Vizyon pair. Every principle is a behaviour a competitor could plausibly contradict, not an adjective, and proof points at checkable artefacts (the products, the blog, this site) instead of aggregates. The principles must not restate the home page's process steps: home says what happens in what order, About says why. The English page deliberately omits the blog link, because `/en/blog/` is empty. Section order and rationale are in `docs/content-decisions.md`.
   - **The home pages** carry a user-picked hero (photo card on the right, `eager`/`fetchpriority="high"` as the LCP candidate), a static decorative background (the same three `.hero-dots` / `.hero-spot` / `.hero-grain` divs on both home pages, so change both) and a process section whose guide line fills red with the visitor's scroll (`.process-fill`). Details are in `docs/content-decisions.md`. The process `steps` live in each home page's frontmatter and make promises (timeline and cost in writing, maintenance after launch) that must stay true. **No fixed demo or release interval may be promised anywhere.** "A working version every two weeks" was removed from every page on 2026-09-23, because the team does not work to that cadence.

### Deliberate decisions (don't "fix" these)

- **Site copy speaks in a corporate, serious register** (the user's call, 2026-09-23: they called the home hero line and the About page "hiç profesyonel değil" and asked for "kurumsal ve ciddi" copy). Turkish copy states things plainly, in the present continuous or a neutral passive ("netleştiriyoruz", "belgelenir"). Use formal verbs ("yazılı olarak belirlemek", "iletişime geçebilirsiniz") and noun-phrase headings rather than questions ("Projelerde öngörülebilirlik", not "Neyi düzeltmeye çalışıyoruz?"). Leave out developer idioms ("tek satır kod yazılmadan"), punchy "X değil, Y" contrasts and aphorisms, cute closing lines ("Geriye konuşulacak sürpriz kalmıyor"), colloquial verbs ("yazılı veririz", "size yıkmayız") and self-praise adjectives such as "dürüst". English copy follows the same register. This rule is about tone only: the substance rules above still hold, and no promise may get stronger in the rewording. Whether blog posts must follow it too has not been decided, so ask before rewriting one.
- **Brand palette is white/black/red, plus one blue for actions** (see the next bullet). Red is an accent color only — logo, step numbers, card hover borders — never a background or text color for content. It lightens to `#ff4d57` in dark mode because `#e50914` drops below the contrast threshold on a dark ground.
- **Orange was tried and rejected** (2026-08-28, at the user's request then their call to drop it). Two things killed it: white text on any real orange lands at 2.8:1, so an orange button would have needed dark text and become the only dark-text button on the site; and orange can't be a text color on white at all, making it a fill-only half-color. It also sits ~28° from the brand red, close enough to read as "the red slipped" rather than a second color. Don't reintroduce it as a third accent without a job of its own.
- **Filled buttons are blue, not red** (changed 2026-08-28 at the user's request): a filled red rectangle reads as "delete / cancel / warning", the wrong signal for a confirming action. Primary buttons use the `--color-action` / `--color-action-dark` tokens (`bg-action` / `hover:bg-action-dark`) defined in `src/styles/global.css`; secondary buttons stay outlined neutral. The rule that settled out of this: **blue means clickable, red means brand.** Anything that invites a click — filled buttons, "read more" links, the colour a card title turns on hover — uses `action`; red is reserved for identity and decoration: the logo, the step numbers on the home page, the `hover:border-brand/40` card outline. The one exception is the white pill on a product panel, where blue would clash with the product's colour (see the product teasers bullet above).
- **Language coverage is asymmetric on purpose.** Turkish has published blog posts; English has none, so `/en/blog/` renders the `blog.empty` string. All three products (İbadet Rehberim, Dernek Asistan and QR Menü) are published in both languages; the home page shows only the first two by `order`, so QR Menü (`order: 3`) appears on the product listings but not on the home. The empty English blog is expected output, not a bug to chase.
- **Logo and favicon are the İ monogram** (black tile, white body with a diagonal cut, red dot centered above). Sources live in `brand/` (`logo.svg` plus PNG exports at 256/512/1024); the deployed favicon is `public/favicon.svg`, and `BaseLayout` also points the JSON-LD `logo` field at it. **The SVG is not the only favicon**: Google Search reads only raster favicons (BMP, GIF, ICO, PNG, JPEG, PPM, TIFF) and showed a grey placeholder house next to every result until 2026-09-28, when `public/favicon.ico` (16/32/48), `public/favicon-96x96.png` and `public/apple-touch-icon.png` (180, full-bleed square because iOS masks its own corners) were added with the matching `<link>` tags. `scripts/icons.mjs` (`npm run icons`) draws all of them, plus the social-media profile photos in `brand/social/` (its README says which file goes to which platform), from `brand/logo.svg` by text transforms of that file, and it throws if the SVG's three elements no longer match. If the mark changes, edit `logo.svg`, run the script, and regenerate the `brand/` PNGs and `favicon.svg` by hand. The script imports `sharp`, which is not a direct dependency: it relies on Astro's copy in `node_modules`.
- **Names inside `src/` are English, content is Turkish.** Asset folders and image files use English names (`_images/`, `screen-prayer-times.png`) even though the copy they carry is Turkish. The Turkish segments under `src/pages/` are the deliberate exception — those are the public URLs, not internal names. Project images live in `src/content/projects/_images/<proje-slug>/` and are referenced from frontmatter with paths relative to the markdown file, so Astro optimizes them (`image()` in the collection schema).
- **Each product image is generated with exactly one set of options**, from `productImageOptions(image)` in `src/utils/product.ts`: portrait phone screens get `PRODUCT_IMAGE_WIDTH` (640) at default quality; landscape desktop screenshots (Dernek Asistan) get `PRODUCT_WIDE_IMAGE_WIDTH` (1984) at `quality: 'max'`, because default WebP compression smears fine UI text (WebP is still ~40 KB at that setting). `'max'` is keyed on the source being PNG; a landscape JPEG photo (the QR Menü cover) gets the same width at default quality, since `'max'` turned that photo into a 700 KB WebP (2026-09-28) and a photo has no UI text to protect. Asking for the same source with a second set of options makes Astro emit a second file that the browser also downloads, and `ProductPage` builds the JSON-LD `screenshot` URLs from the same call as the visible `<img>`, so every component must spread the helper rather than pass its own `width`/`quality`. Each width is 2× the widest place that shape is displayed, so 2× screens don't upscale it — which means **desktop screenshots must be captured at DPR 2** (Chrome DevTools device toolbar → DPR 2 → Capture screenshot; a 1× capture is built at its own width and stays soft on Retina; Astro never enlarges). `isLandscape()` also switches the layout: on the product page a phone screen sits beside the text in a capped column while a landscape shot drops below the text at full container width (hero and feature rows); on the product panel a phone screen stands as a phone and a landscape shot slides in from the edge. `isScreenshot()` (PNG source) is the second switch: only a landscape *screenshot* drops below the hero text — a landscape *photo* (the QR Menü cover, JPEG) stays in the half column at column width, because a photo has nothing to read and full width made it swallow the page (the user's call, 2026-09-28). Save screenshots as PNG and photos as JPEG, since both the quality rule and this layout key on the format. Change the constants, not the individual `<Image>` calls.
- **Store badge art is optional at build time.** `StoreBadges.astro` checks `public/badges/` on disk and falls back to its own text button when the official SVG/PNG is missing, so the repo builds without shipping Apple's and Google's assets. The brand constraints it encodes (App Store first, equal 48px heights, no recolouring or cropping, untranslated wordmarks, one file per language) come from those vendors' guidelines — `public/badges/README.md` has the download links and the rules.
